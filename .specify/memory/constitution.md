# QuickFlow Constitution

## Core Principles

### I. Pinned Stack (NON-NEGOTIABLE)
Every build, dependency and command MUST use exactly the versions pinned below (from the `stack`
table of `project.config.yaml`). No step may upgrade, downgrade or pick a version from memory, and
`@latest` MUST NOT appear in any command or manifest. Where a version is "latest release at setup",
it is looked up once, pinned in the manifest, and never changed afterwards.

| Component | Version |
|---|---|
| Java | JDK 25 (LTS) |
| Spring Boot | 4.1.1 (Maven wrapper, generated by start.spring.io) |
| springdoc-openapi-starter-webmvc-ui | 3.1.1 |
| springdoc-openapi-maven-plugin | latest release at setup, pinned in `pom.xml` |
| JaCoCo Maven plugin | latest release at setup that supports Java 25, pinned in `pom.xml` |
| Database | H2, version managed by Spring Boot |
| Backend tests | spring-boot-starter-test, spring-boot-starter-webmvc-test, spring-boot-starter-data-jpa-test (Boot-managed) |
| Node.js | 24.x LTS, ≥ 24.15 |
| Angular | 22.2.0 (standalone components, signals, zoneless) |
| API client | @openapitools/openapi-generator-cli 2.41.0, generator `typescript-angular` |
| Playwright MCP | @playwright/mcp 0.0.82, chromium, headless |
| spec-kit | v1.0.11 |

Rationale: the loops restart every session; pinned versions keep every session building the same thing.

### II. Independent Verification (NON-NEGOTIABLE)
- Every dev phase MUST be verified by the testing loop before it counts as done: curl checks for
  backend-layer phases, Playwright MCP steps for frontend-layer phases, plus the runner's unit-test run.
- Dev loops MUST NOT verify their own work: they write no verdicts, run no curl or Playwright,
  and never mark a phase `passed`.
- Playwright MCP MUST always run headless; no browser window ever opens.
- Checks are written from the acceptance criteria and the swagger, never from the code under test.
- Every `pass` MUST point to its evidence (command output, screenshot, report file).

Rationale: work checked by its author is not checked.

### III. Backend Unit Tests First (NON-NEGOTIABLE)
- Backend unit tests are required and written before the code they test.
- Every business rule (PRD §7 rules 1–14, cited as BR-1..BR-14) and functional requirement MUST
  have at least one named test,
  e.g. `@DisplayName("BR-11: EndDateTime must be after StartDateTime")`.
- Three kinds of test: domain unit tests (plain JUnit + AssertJ, no Spring context, fixed
  `java.time.Clock`); web-slice tests (`@WebMvcTest` + `MockMvcTester`, services mocked with
  `@MockitoBean`: happy path, 400 with the error body shape, 404, query parameters);
  persistence-slice tests (`@DataJpaTest` on H2: custom queries, the unique (habit, date)
  constraint, cascades, deleted rows never returned).
- `./mvnw verify` MUST pass, with line coverage ≥ 80% on `com.quickflow.domain` once that package
  has classes. A failing test or low coverage fails the phase like a failing curl check.
- Frontend unit tests are optional.

Rationale: business rules are the part curl can't check thoroughly.

### IV. Domain Separate from UI, Time from a Clock
- Business logic lives in the backend `com.quickflow.domain` package; controllers and the UI hold
  no business rules.
- Domain services take a `java.time.Clock` bean and MUST NOT call `now()` without it.
- Time-dependent values (plan status, rest time, due today, overdue, completed today) are computed
  on the server when read, from stored values and the clock; nothing is kept up to date by a
  background job, so they stay correct after the app is closed and reopened.
- One time zone for the whole app: `app.timezone` from `project.config.yaml`
  (currently `Africa/Cairo`). The clock uses it, the backend exposes it to the frontend, and the
  frontend displays date-times in it.
- Rest time is the time left until `EndDateTime`, shown only between `StartDateTime` and
  `EndDateTime`; the frontend recomputes it from `EndDateTime` every second.

Rationale: keeps rules testable and prevents the browser and the server from disagreeing at midnight.

### V. No Guessing
- Something is known only if it is written in the PRD, `spec.md`, `plan.md`, the contract,
  this constitution, `project.config.yaml` or the reviewer notes, or it was checked just now
  (code, installed library sources or docs, `--help`, a small compile).
- An unknown requirement becomes a question (`[NEEDS CLARIFICATION]` while planning, `## Questions`
  while implementing); the session stops instead of choosing.
- An unknown technical fact is checked before code relies on it; if it can't be checked, it
  becomes a question.
- Assumptions are listed under `## Assumptions` in the review file and are built only after approval.
- A test check whose expected result isn't stated is `unclear`, never a pass.

Rationale: a guessed requirement is a bug the reviewer never got to see.

## Technical Constraints

- **Backend**: Spring Boot REST API under `/api`, JPA + H2. Profiles: default = file
  `./data/quickflow` (persists between runs); `test` = file `./data/test` (deleted by the runner
  before every test session); `openapi` = in-memory H2 on port 18080, used only by the
  springdoc-openapi-maven-plugin during `./mvnw verify` (spring-boot-maven-plugin `start`/`stop`
  around the integration-test phase), which writes `target/openapi.json`. Swagger UI at
  `/swagger-ui`, docs at `/v3/api-docs`.
- **API contract**: backend planning writes `contracts/openapi.yaml` (OpenAPI 3.1) before any code;
  from implementation on, the generated `loops/backend-dev/outputs/openapi.json` is the swagger.
- **Frontend**: Angular app generated from `openapi.json` with the pinned generator; the dev server
  proxies `/api` to the backend (`proxy.conf.json`), so no CORS configuration is added.
- **Performance**: create/update/delete/filter actions complete in under 500 ms (PRD §10).
- **Data**: deleted rows are never returned by normal queries (BR-14).

## Development Workflow & Quality Gates

- Work is done one phase per session through `scripts/run-loop.sh`; each phase of `tasks.md` is one
  milestone.
- No phase is implemented until its review file is `approved` at the review gate.
- `/speckit-tasks` is always run with tests requested; `/speckit-implement` is always scoped to one
  approved phase.
- A milestone has at most 3 attempts; after the third failure it is `blocked`, and the phases that
  depend on it are blocked with it.
- The runner makes every commit locally (one `(verified)` commit per finished phase). Nothing is
  pushed automatically: every push goes through `scripts/review-commits.sh` after the commits are
  reviewed. No session runs git.
- A loop is complete only when every phase is `done` or `skipped` and `/speckit-converge` reports
  Converged.

## Governance

This constitution overrides any other practice in this repository. Plans (`/speckit-plan` gates),
analysis (`/speckit-analyze`) and convergence (`/speckit-converge`) check work against it; a broken
MUST rule is a CRITICAL finding. No loop session may change this file: amendments are made by the
project owner interactively, recorded with a version bump (MAJOR: a principle removed or redefined;
MINOR: a principle or section added or materially expanded; PATCH: wording), and committed as an
engine change so later runs record the new `engine_version`.
