**Branch**: `001-quickflow` | **Date**: 2026-09-24 | **Spec**: [spec.md](spec.md)

From implementation on, the API client is generated from `loops/backend-dev/outputs/openapi.json`.

## Summary

An Angular single-page app with six pages reachable from persistent navigation (Dashboard, Tasks, Habits,
Learning Resources, Todo Plans, Settings). Every page talks to the backend `/api` through the client
generated by `@openapitools/openapi-generator-cli` 2.41.0 (`typescript-angular`) into
`frontend/src/app/api`. The UI holds no business rules (Constitution IV): statuses, overdue, streaks,
progress and rest seconds come from the API; the UI only formats them, displays date-times in the app time
zone from `GET /api/app-info`, recomputes the rest time from `endDateTime` every second, and re-reads plans
when a plan's start or end is reached. Validation messages come from the API's 400 problem details
(`errors[{field, message}]`) and are shown next to the named field.

**Primary Dependencies**: Angular 22.2.0 (standalone components, signals, zoneless; scaffolded by the runner with

**Storage**: none in the frontend (all state is on the server, NFR-3); `localStorage` only for the ids of plans whose
start notification was already shown (research R-6, assumption FA-2)

**Testing**: no frontend unit tests (Constitution III: optional; `layers.frontend.test` is empty). Each phase is verified

`data-testid` selectors pinned in [contracts/ui-contract.md](contracts/ui-contract.md) (assumption FA-1)

**Target Platform**: desktop browser (chromium for the checks) on the user's machine, dev server `npm start` at
http://localhost:4200, `/api` proxied to http://localhost:8080 by `frontend/proxy.conf.json`

**Project Type**: web application, frontend layer (the Spring Boot backend is a separate layer)

**Performance Goals**: every create/update/delete/filter action gives feedback < 500 ms (NFR-1, SC-004): one request per
action, the list is updated from the response or one re-read

**Constraints**: date-times displayed in the app time zone (Constitution IV), never the browser's; rest time updated every
second (NFR-2); no CORS config (proxy); no business rules in components; only pinned versions

**Scale/Scope**: one user, six pages, ~15 components, hundreds of rows per list, no pagination

**Structure Decision**: Web application, frontend layer only (`frontend/`). Pages are standalone components under
`pages/<area>/`, lazily loaded by the router; cross-page services live in `core/`, small presentational pieces in
`shared/`. Components call the generated services directly (no hand-written HTTP wrappers) and keep their state in
signals.

## Design highlights

- **No business rules in the UI**: `overdue`, `doneForCurrentPeriod`, `currentStreak`, plan `status`,
  `progressPercent`, `restSeconds`, all dashboard counts come from the API. The UI decides only what to display.
- **Time**: `ClockService` reads `GET /api/app-info` once at start-up (`timeZone`, `now`), keeps the offset
  between server and browser time, and exposes a `now` signal ticking every second. Dates and date-times are
  formatted with `Intl.DateTimeFormat` and `timeZone` = the app zone. The plan builder's `datetime-local` inputs are
  wall times in the app zone, converted to ISO-8601 with that zone's offset at that instant (research R-3).
- **Rest time and status boundaries**: a plan card shows rest time only when the API says `IN_PROGRESS` and
  `restSeconds` is not null; it displays `endDateTime − now` every second. When `now` crosses a shown plan's
  `startDateTime` or `endDateTime`, the page re-reads the plans so the status comes from the server (research R-4).
- **Errors**: a 400 problem detail's `errors[]` are shown under the matching field (`data-testid="error-<field>"`);
  404/409 and other errors show `detail` (or `title`) in the notice area. Forms do not pre-validate lengths, so the
  server's message is the one the user sees (FA-3).
- **Default page**: the empty path redirects to the page named by `Settings.defaultPage` (read once per app load).
- **Client regeneration**: every implement session runs `generate_client` (loop step I.8), so the client follows
  the latest backend `openapi.json`; story phases wait for the matching backend story (`backend-dev:USn`).
