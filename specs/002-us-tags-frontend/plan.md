# Implementation Plan: Task tags (frontend layer)

**Branch**: `002-us-tags` | **Date**: 2026-09-26 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/002-us-tags-frontend/spec.md` (copied from `specs/002-us-tags-backend/spec.md`)

**Layer**: `frontend` (`frontend/`, loop `frontend-dev`, `contract_from: backend`). Planned against the backend
swagger [specs/002-us-tags-backend/contracts/openapi.yaml](../002-us-tags-backend/contracts/openapi.yaml).
From implementation on, the API client is generated from `loops/backend-dev/outputs/openapi.json`.

This feature extends the existing Tasks page of `specs/001-quickflow-frontend` (User Story 1 "Manage tasks",
`frontend/src/app/pages/tasks/`). Everything else in the frontend stays as it is.

## Summary

On the Tasks page (`/tasks`) every task row shows the task's tags (from `Task.tags`, as the API returns them:
lower case, alphabetical) with a remove button per tag, and an inline input to add one or more tags to that task
(`POST /api/tasks/{id}/tags`). The toolbar gains a tag filter that is sent as the `tag` query parameter of
`GET /api/tasks` and combines with the existing filters and sort. Removing a tag calls
`DELETE /api/tasks/{id}/tags?tag=`. The UI holds no tag rules (Constitution IV): trimming, letter case, the 1–30
length and the 10-tag limit are all decided by the server; a 400 problem detail's message for field `tags` is shown
under the row's tag input, and the task's tags stay as they were because the list is only re-read after a success.

**Primary Dependencies**: Angular 22.2.0 (standalone components, signals, zoneless), `@angular/common/http`, the API
client generated by `@openapitools/openapi-generator-cli` 2.41.0 (`typescript-angular`) into `frontend/src/app/api`.
No new npm dependency (Constitution I).

**Storage**: none in the frontend; tags live on the server with the task (FR-008)

**Testing**: no frontend unit tests (Constitution III: optional; `layers.frontend.test` is empty). The story phase is
verified by the testing loop with Playwright MCP (headless chromium) from AC-US1-1..6, using the selectors pinned in
[contracts/ui-contract.md](contracts/ui-contract.md) before any code is written

**Target Platform**: desktop browser, dev server `npm start` at http://localhost:4200, `/api` proxied to
http://localhost:8080 by `frontend/proxy.conf.json` (existing)

**Project Type**: web application, frontend layer (the Spring Boot backend is a separate layer)

**Performance Goals**: add tag, remove tag and filter by tag give feedback < 500 ms (SC-002): one request per action,
then one re-read of the list

**Constraints**: no business rules in components (no client-side trimming, case folding, length or count checks);
only pinned versions; generated client never edited by hand

**Scale/Scope**: one page changed (`/tasks`), one new small component, up to 10 tags per row

**Structure Decision**: Web application, frontend layer only. The tag UI of one row is a small standalone
presentational component next to the Tasks page (`pages/tasks/task-tags.ts`), like `task-form.ts`; the page keeps
the API calls, notices and error mapping, as it already does for the other row actions.

## Design highlights

- **Show tags** (AC-US1-1, FR-002): each row renders `task.tags` in API order as chips; no sorting or case change in
  the UI.
- **Add tags** (FR-001, AC-US1-1): the row's input takes one or more tags separated by commas (FA-T2); the page sends
  `addTaskTags(id, { tags: <the comma-separated parts, as typed> })`. On 200 it shows a notice and re-reads the list
  (so a tag filter in force is applied); the input is cleared because the row's task object is replaced. On 400 the
  `tags` field message is shown under that row's input and nothing is re-read, so the tags shown stay unchanged
  (AC-US1-4, AC-US1-6); messages for other fields go to a notice. 404 → notice + re-read.
- **Remove a tag** (FR-005, AC-US1-3): each chip has a remove button → `removeTaskTag(id, tag)`, notice, re-read.
- **Filter by tag** (FR-004, AC-US1-2, AC-US1-5): toolbar text input sent as `tag` (blank = omitted), re-read on
  input like the search box; disabled in the Overdue view like the other filters (`listOverdueTasks` has no `tag`);
  a non-blank tag counts as "filtered" for the empty-state message ("No tasks match").
- **Client regeneration**: the story phase regenerates the client from the backend's `openapi.json` first and checks
  the generated names and parameter order before using them (research R-1); the phase waits for the backend story
  (`backend-dev:US1`).
